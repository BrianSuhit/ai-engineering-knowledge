**Qué es en criollo el tema:**

Es una librería para **definir contratos de datos y validarlos** usando los tipos nativos de Python (`str`, `int`, `bool`, `list`). Si los datos cumplen el contrato, te devuelve un objeto limpio; si no lo cumplen, te frena en seco y te dice exactamente qué falló.

**Qué problema resuelve:**

Python por defecto no valida tipos: si a una función le pasás un texto donde esperaba un número, el programa sigue de largo y explota 20 líneas más tarde. Pydantic resuelve la entrada de datos sucios (de un formulario web, una base de datos o un JSON de una IA), asegurando que dentro de tu sistema los datos siempre tengan la forma y el tipo correctos.

**Ejemplo mínimo de código:**

El flujo estándar de Pydantic en cualquier proyecto del mundo consta de tres pasos: **definir el molde → pasarle datos crudos → usar el objeto validado**:

```python
from pydantic import BaseModel

# Paso 1: Definís el contrato heredando de BaseModel
class Usuario(BaseModel):
    id: int
    nombre: str
    activo: bool = True  # Campo opcional con valor por defecto

# Paso 2: Le pasás datos crudos (ej: un diccionario que vino de una API)
datos_crudos = {"id": "10", "nombre": "Carlos"}

# Paso 3: Pydantic valida, convierte ("10" -> 10) y crea el objeto
usuario = Usuario(**datos_crudos)

print(usuario.id)      # 10 (lo convirtió automáticamente a entero int)
print(usuario.activo)  # True (aplicó el default)
```

**La trampa o error común:**

**Creer que Pydantic solo valida (hace coerción de tipos):** Si en un campo ponés `edad: int` y le mandás el string `"25"`, Pydantic **no** tira error; asume que fue un string convertible y lo transforma en el entero `25` . Solo explota con `ValidationError` si le mandás algo inconvertible como `"veinticinco"`.

**Usar dict(...) en vez de .model_dump():** En versiones modernas de Pydantic (v2), para volver a convertir el objeto a un diccionario común de Python no se usa `dict(usuario)`, sino su método oficial `usuario.model_dump()`.

### **Parámetros más usados dentro de `Field(...)` en Pydantic**

Cuando definís atributos en una clase que hereda de `BaseModel`, importás `Field` de Pydantic (`from pydantic import Field`) para agregarle reglas o metadatos al campo:

- **description="..."**: Explica en lenguaje natural qué representa el dato. En IA es clave porque **Gemini lee esta descripción** en el JSON Schema para entender qué información precisa debe extraer o generar.
- **default=...**: Define el valor por defecto si no viene el dato (ej: `default=None` o `default=0`).
- **default_factory=...**: Se usa cuando el valor por defecto es mutable, como una lista o diccionario vacío (ej: `default_factory=list`).
- **alias="..."**: Permite que en el JSON la clave se llame de una forma y en tu código Python de otra (por ejemplo, en tu `models.py` usaste `is_compatible = Field(alias="es_compatible")`).
- **Límites numéricos:** `gt` (*greater than*), `ge` (*greater or equal*), `lt` (*less than*), `le` (*less or equal*). Ej: `Field(ge=0, le=100)`.
- **Límites de texto:** `min_length=...`, `max_length=...` para controlar la cantidad de caracteres.

son métodos nativos incorporados en Pydantic versión 2 - usados con api de gemini

- **MiModelo.model_json_schema():** Agarra tu clase de Python y la traduce automáticamente a un diccionario con formato estándar de **JSON Schema**. Vos se lo entregás a Gemini en el parámetro `response_format={"schema": ...}` para "marcarle la cancha" y obligarlo a respetar esa estructura.
- **MiModelo.model_validate_json(...):** Gemini te responde texto plano (`interaction.output_text`). Este método de Pydantic lee ese texto string, corrobora que sea un JSON válido según tu modelo y lo transforma en un objeto real de Python.
